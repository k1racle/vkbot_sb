## 2. Плюс-слова: реагировать только на нужные комментарии

### Обязательное поведение — реализовано

- [x] У каждой кампании своё необязательное поле «Плюс-слова» рядом со стоп-словами.
- [x] Пустое поле отключает проверку плюс-слов, остальные фильтры сохраняются.
- [x] Достаточно одного слова или фразы из списка; без совпадений нет отправки и ожидающего подарка.
- [x] Стоп-слова имеют приоритет, минимальная длина, тестовый режим и защита от повторов сохраняются.
- [x] Фильтр действует и при прямой отправке, и при приглашении в чат, на поддерживаемые комментарии к постам и видео.
- [x] Проверки подписки и разрешения на личные сообщения не обходятся.
- [x] Очистка поля выключает фильтр; у старых кампаний значение пустое.
- [x] Понятная причина пропуска в статистике: «Нет плюс-слова» (`plus_word_missing`).

Примеры при плюс-словах `подарок` и `хочу скидку`:

| Комментарий | Проверка плюс-слов | Итог при выполнении остальных условий |
| --- | --- | --- |
| «Хочу подарок!» | Совпадение | Реагировать |
| «Очень хочу скидку» | Совпадение фразы | Реагировать |
| «Красивое фото» | Нет совпадений | Не реагировать |
| Есть плюс-слово и стоп-слово | Совпадение есть, но действует запрет | Не реагировать |
| Любой комментарий, список плюс-слов пуст | Проверка отключена | Решение по остальным условиям |

### Правила совпадения первой реализации

Реализовано: целые слова/фразы, без учёта регистра, с нормализацией е/ё и пробелов. Разделители — новая строка или запятая, без автоматического склонения. Изначальные рекомендации:

- Один элемент на строку; элементом может быть слово или фраза.
- Без учёта регистра; начальные/конечные пробелы и повторяющиеся элементы не влияют на результат.
- Рекомендуемый режим — целое слово или последовательность слов фразы, а не случайное вхождение внутри другого слова. Например, `код` не должен срабатывать на `кодекс`.
- Знаки препинания вокруг слова не мешают совпадению. Для фраз нормализовать разделители; точное поведение зафиксировать примерами в тестах.
- Предлагается считать «ё» и «е» одинаковыми.
- Не угадывать словоформы, опечатки и смысл автоматически: `подарок` и `подарки` — отдельные варианты. Это можно расширить позже.
- Обычный фильтр не понимает отрицание: «не хочу подарок» содержит `подарок`. Если это важно для акции, добавить «не хочу» в стоп-фразы.
- Текущий способ сопоставления стоп-слов не менять молча вместе с добавлением нового поля.
- Режим «все слова из списка» и сложные логические выражения не требуются для первой версии.

### Полезное дополнение к фильтру — ещё на согласование

«Проверить комментарий» в карточке кампании: вставить текст и увидеть, какие текстовые условия прошли, какие нет и что было бы следующим действием. Проверка ничего не публикует, не создаёт подарок и не расходует промокод. Реальные подписка и разрешение пользователя либо явно проверяются отдельно, либо помечаются как неизвестные, а не выдумываются.

## 3. Развитие админки: проекты, выгрузки и сценарии

### 3.1. Интерфейс

Текущий этап: общая страница `/projects`, создание и настройка группы, переход в её панель `/p/<id>/admin` и переключение проектов. `<id>` — внутренний ID проекта, не номер сообщества VK. Настройки, кампании, сценарии, клиенты, рассылки, общение и статистика относятся к проекту из URL; выбор в одной вкладке не меняет другую.

В форме проекта задаются название, ID сообщества, токен, секрет Callback API и код подтверждения; ссылка на чат редактируется в настройках выбранного проекта. Проверка через `groups.getById` подтверждает только принадлежность токена группе. Полная диагностика прав, доставки и подключения Callback этим не реализуется. Новые адреса Callback имеют вид `/vk/callback/<id>` на существующем домене; автоматической регистрации сервера в VK нет.

Новая группа создаётся на паузе и требует явного включения. Пауза сохраняет доступ к панели и данным, блокирует автоматические ответы и реальные тестовые отправки; доступны подтверждение Callback API и явная проверка токена. Проверенные по сообществу и секрету обычные события на паузе получают `ok` и отбрасываются: сохраняемой входящей очереди нет, после включения такие события не проигрываются. Отписки «Стоп»/кнопкой и события разрешения/запрета сообщений сохраняются без исходящих ответов. История и уже созданные очереди рассылок сохраняются; готовые задания продолжаются после включения автоматически с учётом отписок. Отдельная пауза/отмена рассылки остаётся в силе. Начатый сетевой запрос может завершиться.

Приёмка текущего этапа:

- [ ] Проверить отображение выбранной группы при настройке и перед отправкой рассылки, независимый выбор клиентов в двух проектах и работу нескольких вкладок.
- [ ] Проверить создание проекта без отправок, включение, паузу, подтверждение Callback и блокировку реальных тестовых отправок на паузе.
- [ ] Проверить адреса API, формы, перенаправления и файлы в контексте выбранного проекта.

Следующие этапы:

- [ ] Аватары, сводная статистика и расширенная диагностика проблем на общей странице проектов.
- [ ] Копирование кампаний и сценариев между собственными проектами как независимых шаблонов. Проверять и переназначать ссылки на кампании и файлы; не копировать клиентов, токены, отписки, выданные подарки и историю отправок.

### 3.2. Где хранятся настройки

В админке проекта и базе данных:

- ID и название сообщества;
- токен VK, секрет Callback API и код подтверждения;
- ссылка `{chat_url}` и параметры общения;
- кампании, промокоды, фильтры, сценарии, менеджеры и параметры рассылок.

В ENV приложения:

- `DATABASE_URL`, `POSTGRES_*` и другие параметры инфраструктуры;
- необязательный `PUBLIC_BASE_URL=https://vkbot.it-sarkisian.ru` — существующий публичный адрес панели для отображения Callback за Nginx с завершением TLS; новые домены или стеки не нужны;
- `ADMIN_SESSION_SECRET`;
- `ADMIN_USERNAME` и `ADMIN_PASSWORD` общего владельца панели;
- необязательный `PROJECTS_ENCRYPTION_KEY` — ключ Fernet (32 байта в URL-safe Base64), либо файл ключа по `PROJECTS_KEY_FILE`;
- технические параметры: например, `LOG_LEVEL`, `BACKGROUND_JOBS_ENABLED`, общая версия API при необходимости.

`PUBLIC_BASE_URL` — проверяемый HTTP(S)-адрес без пути, query-параметров, фрагмента и учётных данных. Для VPS рекомендуется HTTPS; HTTP используется при локальной проверке. Пустое значение сохраняет формирование ссылки из URL входящего запроса, который за прокси может иметь схему HTTP. Настройка публичного адреса не регистрирует Callback в VK и не требует доверия к произвольным заголовкам прокси.

В реестре проектов токен, секрет Callback API и код подтверждения зашифрованы Fernet; ключ находится вне БД. Если `PROJECTS_ENCRYPTION_KEY` не задан, ключ автоматически создаётся и сохраняется в `data/projects.key`; путь можно изменить через `PROJECTS_KEY_FILE`. Файл должен переживать пересоздание контейнера. Нужна отдельная защищённая копия фактически используемого ключа, включая вариант из ENV. Копии зашифрованной базы без этого ключа недостаточно. Замена ключа случайным новым значением не восстанавливает доступ и не является ротацией.

Прежние `VK_GROUP_ID`, `VK_GROUP_TOKEN`, `VK_CALLBACK_SECRET`, `VK_CONFIRMATION_CODE` импортируются один раз для существующей группы. Сохраните их до переноса и проверки; после импорта изменение ENV не подменяет сохранённые секреты. При отсутствии VK ENV используется `group_id=0`: новая установка открывает пустой реестр для настройки через панель. Новых обязательных ENV нет; последующие группы добавляются без перезапуска контейнера. Запасная отправка общим токеном другой группы не предусмотрена. Не возвращать полные секреты в браузер и не писать их в журнал; замена реквизитов выполняется через панель.

При импорте сохраняется и снимок прежних настроек по умолчанию для исходной группы: общение, менеджеры, тестовый режим, промо-параметры. Значения в её `bot_settings` имеют приоритет. Новые проекты получают исходные настройки без наследования этих значений. Старые групповые ENV разрешается убрать только после проверки импорта и сохранения резервной копии; инфраструктура и ключ шифрования остаются.

### 3.3. Разделение данных и обработка событий

**Реализованный выбор:** PostgreSQL использует отдельную схему `project_<id>` для каждого нового проекта в общей базе. Импортированная группа продолжает работать с прежними таблицами в исходной схеме, с сохранением ID и истории. Для SQLite каждый новый проект получает отдельный файл `project_<id>.db` рядом с исходной БД; legacy-проект сохраняет прежний файл. Реестр проектов хранится отдельно от таблиц данных новых проектов. Новые вложения размещаются в `data/projects/<id>/`, прежние пути файлов импортированной группы сохраняются.

Это сознательная замена первоначального варианта с `project_id` в каждой таблице. Принадлежность строки, уникальность и выбор очереди задаются схемой/файлом БД, выбранными на сервере. Контекст проекта передаётся через `ContextVar`, настройки и сессия БД разрешаются в этом контексте без переключения глобального токена или движка. Для резервной копии нужны все схемы, а не только `public`.

Контроль изоляции перед выпуском:

- [ ] Для каждого объекта определить владельца-проект: настройки, кампании, сценарии, файлы, клиенты, диалоги, менеджеры, комментарии, подарки, аудит отправок, рассылки и их получатели.
- [ ] Один VK-пользователь может существовать в нескольких проектах с разными состояниями диалога, ответственными менеджерами, разрешениями и отписками.
- [ ] Уникальность клиентов учитывать как «проект + пользователь»; постов и общей кампании — в пределах проекта. Пересмотреть существующие глобальные ограничения и ключи повторной обработки.
- [ ] Входящие события определяют проект на сервере; дополнительно проверяются ID сообщества и его секрет. Код подтверждения берётся у этого же проекта. Несовпадение проекта, сообщества и секрета не допускает обработки.
- [ ] Все исходящие вызовы VK, проверки подписки и разрешения используют ключ нужного проекта.
- [ ] Проверить передачу контекста проекта обработчикам, фоновым задачам и поточным вызовам. Не переключать глобальный объект настроек между группами во время запросов: события могут идти одновременно.
- [ ] Проверять принадлежность объектов проекту в API и работе с файлами, а не только скрывать чужие записи в интерфейсе. То же относится к поиску, статистике, выгрузкам, кэшам и фоновым заданиям.
- [ ] Очереди и ограничения отправок учитывать по проектам. Задержка или проблема ключа одной группы не должна останавливать остальные.
- [ ] Разрешение на сообщения или согласие на рассылки одной группы не использовать для другой. Отписки также разделяются по группам.
- [ ] Для повторов, отложенных действий и перезапуска сохранять исходный проект; изменение текущего проекта в браузере не влияет на уже созданную очередь.

Проверка принадлежности данных нужна даже для внутренних проектов. Серверные проверки доступа и тесты на подмену проекта опираются на [рекомендации OWASP по изоляции проектов](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html); общий владелец не устраняет риск случайной отправки не той аудитории.

### 3.4. Сотрудники

В текущем этапе общий вход владельца из ENV видит и настраивает все проекты. Отдельные аккаунты сотрудников, ограничения доступа по проектам, RBAC и персональный аудит администраторов **не реализованы**. Настроенные VK ID менеджеров определяют работу обращений и не предоставляют отдельный вход в веб-панель.

План отдельного этапа:

- [ ] Если сотрудникам нужен вход в админку, выдавать им отдельные учётные записи и доступ к назначенным проектам; не раздавать общий пароль владельца.
- [ ] Разделить работу с диалогами и права на ключи, публикацию сценариев и массовые рассылки. Точный набор ролей определить по обязанностям команды.
- [ ] Доступ сотрудника к админке не подменяет права сотрудника в самом VK.
- [ ] Сохранять журнал важных действий: кто менял ключи и настройки, публиковал сценарий, запускал/отменял рассылку.
- [ ] Не добавлять публичную регистрацию и кабинеты сторонних клиентов.

- [ ] Сначала выполнить миграцию на копии данных и согласовать окно обновления. На время переноса исключить одновременную работу старых и новых обработчиков/очередей.
- [ ] Проверить однократный импорт существующих настроек VK в первый проект SARKISIAN. Реализация сохраняет текущие таблицы и пути файлов; массовое переписывание строк с новым `project_id` не требуется. После пустой первичной инициализации позднее добавление `VK_*` не запускает импорт заново.
- [ ] Сохранить ID, историю выдач, ожидающие подарки, отписки и состояния очередей. Миграция сама по себе не должна заново отправлять промокоды или запускать черновики рассылок.
- [ ] Проверить сохранённый `/vk/callback` только у импортированной группы и `/vk/callback/<id>` у каждого проекта на том же домене. На тестовой копии не регистрировать живой Callback API.
- [ ] Проверить SARKISIAN после перехода, затем подключить вторую тестовую группу и проверить изоляцию.
- [ ] После проверки убрать зависимость работающих групп от общих `VK_*` в ENV. Не оставлять незаметный запасной путь отправки ключом чужой группы.
- [ ] Описать порядок отката с сохранением актуального состояния. Не восстанавливать старую базу поверх новых отправок без сверки истории, иначе возможны повторы.

Приёмка: два проекта с одним и тем же VK-пользователем и одинаковыми номерами постов работают независимо; подмена проекта не раскрывает чужие данные; рассылка не пересекает аудитории; отписка, ошибка токена или пауза одного проекта не затрагивает другой; смена ключа и перезапуск не теряют очередь.

Без отправки сообщений и запросов к VK. Выбор только отмеченных строк, менеджер в отчёте и расширенные параметры имени файла/сводки из списка ниже пока не добавлены.

#### Подробная аналитика — обязательная выгрузка

- [ ] В разделе «Статистика» кнопка «Выгрузить отчёт»: период, проект, кампании, сценарии/версии, рассылки, менеджеры и нужные листы. Применять только подходящие к выбранному отчёту фильтры; не выдавать статистику рассылки за результат кампании без сохранённой связи.
- [ ] Один `.xlsx` с выбранными листами: сводка для быстрого просмотра и отдельные строки для разбора. Предлагаемый состав:

| Лист | Что показывать |
| --- | --- |
| Параметры отчёта | Проект, период, часовой пояс, фильтры, момент снимка, дата начала сбора каждого вида данных и определения показателей |
| Сводка и динамика | По дням: учтённые комментарии, уникальные участники, запросы подарка, успешные отправки промокодов, ошибки, обращения к менеджерам |
| Кампании и публикации | Кампания, тип и ID публикации, ссылка при наличии; подходящие комментарии, пропуски по каждой причине, приглашения, ожидающие и выданные подарки |
| Воронка подарка | Для приглашения в чат: подходящий комментарий → отправленное приглашение → запрос подарка → подтверждённая подписка → отправленный промокод; прямую выдачу считать отдельно |
| Выдачи промокодов | Клиент и ссылка VK, кампания, источник, дата, результат, связанное событие/подарок; конкретный код только если он сохранён для этой выдачи, а не текущий код из изменённой кампании |
| Рассылки | Сводка по рассылке и строки получателей: состояние, число попыток, время отправки, причина пропуска/отмены/ошибки |
| Сценарии и шаги | Сценарий и опубликованная версия, запуски, посещения блоков, выбранные ответы, переходы, завершения, передача менеджеру и ожидание ответа |
| Обращения и менеджеры | Обращение, клиент, запрос менеджера, закрепление, первый ответ, завершение при наличии такого события, ответственный и длительность ожидания |
| Журнал событий | Время, проект, клиент, связанные кампания/публикация/сценарий/рассылка, действие, результат, понятная причина и безопасный код ошибки |

#### Чтобы цифрам можно было доверять

- [ ] Считать события и уникальных людей раздельно; для пользователей явно указывать область уникальности. В общем отчёте по проектам один человек в двух группах остаётся двумя клиентскими записями, а не единым согласием на сообщения.
- [ ] Для воронки выбрать когорту по дате исходного комментария и учитывать её результаты до указанного момента снимка. Рядом показывать числитель, знаменатель и долю относительно предыдущего этапа; при нулевом знаменателе — «нет данных для расчёта», а не ошибочный процент. Отдельно обозначать ожидающие подарки.
- [ ] В режиме прямой выдачи нет этапов приглашения и запроса подарка. Проверка существующей подписки не означает, что бот привёл нового подписчика. Повторные комментарии одного человека и повторные доставки одного события VK не должны умножать число выданных подарков.
- [ ] Динамика за период считается по времени соответствующего действия, а не по текущему статусу старого комментария. Не смешивать её с когортной воронкой без пояснения. Связи этапов сохранять по идентификаторам, а не угадывать по близости времени или одному имени.
- [ ] Тестовые отправки и симулятор отделить от рабочих результатов. Повторные попытки отражать как попытки, но не как новых клиентов или несколько успешных выдач одного подарка.
- [ ] Успешный ответ API на отправку обозначать как «отправлено / принято VK», не как доказанное прочтение. Клики по внешним ссылкам, прочтения, покупки, выручку и использование промокода показывать только при наличии достоверного источника и отдельной реализации учёта; иначе — «не отслеживается». Заказная аналитика зависит от интеграции магазина и не входит автоматически в первый выпуск.
- [ ] Добавить историю переходов состояния: события выдачи и обращения, входы/выходы блоков, выбранные ветки, время и опубликованная версия сценария. Сейчас `ProcessedComment` хранит изменяемый статус, `Conversation` — текущее состояние, а `BotMessage` — успешные отправки без полной привязки к шагам: этого недостаточно для точной ретроспективной воронки и времени каждого шага.
- [ ] Старые данные выгружать в реально имеющемся объёме. Новые показатели собирать с даты внедрения; пустую историю не заменять нулями и не восстанавливать несуществующие этапы по догадкам. Показывать охват истории и ограничения отчёта.
- [ ] Сохранять устойчивые ID и нужные исторические названия/версии, чтобы переименование или архивирование кампании не переписывало прошлые результаты. Полные тексты диалогов и ответы с персональными данными не добавлять в общую аналитику по умолчанию; для них нужны отдельные права и согласованный срок хранения.
- [ ] «Не завершил сценарий» не считать отказом автоматически: человек может ещё отвечать или ждать менеджера. Для показателя прекращённых диалогов сначала определить срок неактивности и исключения. Время реакции менеджеров считать только по зафиксированным запросам/ответам, разделяя календарное время и рабочее, если появится расписание.
- [ ] Экран статистики и файл используют одинаковые определения показателей. Все листы файла строятся по согласованному снимку, даже если во время формирования приходят новые комментарии; параметры и время снимка записаны в отчёте.

Приёмка аналитики: итоговые цифры сверяются с детализацией; проверены границы периода и часовой пояс, повторные события, повторные клиенты, пропуски по фильтрам, отсутствие разрешения, тестовые отправки, обе схемы выдачи, смена версии сценария и несколько проектов. Отдельно проверить неполную старую историю и выгрузку во время поступления новых событий.

#### Доступ, безопасность и большие списки

Эти требования относятся и к клиентам, и ко всем аналитическим листам.

- [ ] Выгружать только данные проектов, к которым сотруднику разрешён доступ. Право экспорта предусмотреть отдельно от простого просмотра клиентов.
- [ ] Для владельца можно добавить явную выгрузку нескольких собственных проектов с обязательными колонками проекта и сообщества; не объединять записи одного VK-пользователя из разных групп в одну и не смешивать их согласия/отписки.
- [ ] Не включать токены, секреты, пароли, служебные ключи и скрытые технические поля в таблицы или имена файлов.
- [ ] Имена и другие пользовательские значения записывать в `.xlsx` как текст, не позволяя библиотеке превращать их в формулы. В тестах проверить значения, начинающиеся с `=`, `+`, `-`, `@`, пробельных и управляющих символов. Если позже появится CSV, нужна отдельная проверка его безопасного открытия; один только экранированный CSV-разделитель не решает проблему. [Описание риска формул в таблицах от OWASP](https://community.owasp.org/attacks/CSV_Injection).
- [ ] Большие выгрузки формировать в фоне с ограничением памяти, не блокируя обработку комментариев и сообщений. Показать состояния «Готовится», «Готово», «Ошибка» и число строк.
- [ ] Скачивание только после проверки входа и доступа к исходному проекту, в том числе если права сотрудника изменились после запуска выгрузки. Не размещать файлы с телефонами в публичной папке или по постоянной открытой ссылке.
- [ ] Временные файлы автоматически удалять по согласованному сроку. Журналировать автора, проект, время, условия и число строк без копирования всех персональных данных в журнал.
- [ ] Пустой результат, отменённая выгрузка, нехватка места и недоступность файла должны давать понятное сообщение, а не останавливать бота.

Приёмка: корректное открытие в Excel; кириллица, телефоны и ID не искажаются; все страницы выбранного набора попадают в файл; чужой проект не попадает в выгрузку; отсутствующие контакты не выдумываются; пользовательский текст не исполняется как формула; проверена выгрузка объёма больше одной страницы и влияние большого задания на скорость ответов бота.

Экспорт в Excel — отчёт для работы, **не полноценная резервная копия бота** и не автоматическая функция обратного импорта.

### 3.7. Обновление VPS и непрерывность работы

По текущим файлам проекта: один контейнер приложения `vk-bot`, отдельный PostgreSQL, именованные тома `postgres_data` и `bot_data`; инициализация/обновление базы выполняется при старте приложения. Это описание конфигурации репозитория, не результат проверки живого VPS.

Локальные проверки хранилища этого этапа используют PostgreSQL 17; рабочий Compose сохраняет PostgreSQL 16 (`postgres:16-alpine`). Результаты нужно указывать с фактической версией: прогон на 17 не заменяет репетицию переноса на рабочей 16. Браузерная проверка проектов в настольном и мобильном размерах пройдена на изолированных данных; реальная регистрация Callback и отправки в VK в неё не входят.

При пересоздании единственного экземпляра приложения возникает перерыв в доступности админки и Callback API. Обычное обновление Compose сохраняет подключённые тома, но это не заменяет проверку совместимости новой версии со старой базой. [Поведение Docker Compose при обновлении контейнеров](https://docs.docker.com/reference/cli/docker/compose/up/).

- [ ] Первым выпускать этап нескольких групп; плюс-слова, Excel-экспорт и расширение конструктора не входят в него и не задерживают его приёмку.
- [ ] Проверить повторную инициализацию реестра, миграции прежних таблиц без потери записей и создание изолированных схем/SQLite-файлов. Выбранная схема сохраняет прежние ограничения внутри каждого проекта; добавление `project_id` ко всем строкам не требуется. Проверка SQLite не заменяет проверку PostgreSQL и его `search_path`.
- [ ] До обновления репетировать перенос на изолированной копии базы и файлов с фиктивными реквизитами всех групп и `BACKGROUND_JOBS_ENABLED=false`. Одной замены `VK_*` недостаточно для уже импортированного реестра: секреты находятся в зашифрованной БД. До их обезвреживания исключить исходящий доступ копии к VK; не регистрировать живой Callback API. Один только тестовый режим комментариев или отключение фоновых задач не блокирует все ручные/входящие вызовы VK.
- [ ] Подготовить образ заранее и измерить длительность миграции на копии. Окно обновления согласовать по результату; не обещать конкретное время или нулевой простой без такой проверки.
- [ ] Сделать согласованную резервную копию перед переносом: полный дамп PostgreSQL со всеми схемами/реестром, `bot_data` и отдельно ключ Fernet. Обеспечить отсутствие непопавших в неё изменений во время финального переключения. `pg_dump` даёт согласованный снимок базы, но не включает записи, появившиеся после начала снимка; порядок остановки записи, снимка файлов и переноса должен учитывать это. [Документация PostgreSQL 16](https://www.postgresql.org/docs/16/app-pgdump.html).
- [ ] Зафиксировать подключение к той же базе и тем же томам. Не удалять тома и не переименовывать стек/тома без явного плана привязки существующих данных.
- [ ] Исключить параллельные реальные отправки старой и новой версий. Дать начатым операциям безопасно завершиться либо сохранить их состояние для проверки/повтора без выдачи нового подарка.
- [ ] Отдельно определить обработку входящих событий в окно обновления. Пауза проекта подтверждает подходящие события ответом `ok` и отбрасывает их, она не заменяет сохраняемую входящую очередь. Не считать повторы VK достаточной гарантией нулевой потери; непрерывный приём требует отдельного решения с сохранением событий и проверкой повторов.
- [ ] После запуска проверить не только `/health`, но и вход, выбранный проект, настройки, файлы, количество клиентов, действующие кампании, ожидающие подарки, отписки и состояние очередей. Полный путь комментарий → подарок проверить только на согласованном тестовом получателе/публикации.
- [ ] Возобновлять автоматические отправки после проверки перенесённого состояния. Импортированный проект сохраняет рабочее поведение, новые создаются на паузе; при включении проекта готовые очереди продолжаются автоматически. Порядок запуска и `BACKGROUND_JOBS_ENABLED` должны исключать отправки до проверки, а сверка истории — случайный повтор старой рассылки или промокода.

Критерий готовности выпуска: показано сохранение существующего поведения и данных, измерено окно переключения, проверены восстановление и повторная обработка событий. Не использовать пароль владельца/полный токен администратора CRM. Названия методов и формат ключа определить при реализации, не выдавать предлагаемые маршруты за существующие.
- [ ] В админке бота — подключение магазина для выбранного проекта: адрес API/витрины, при необходимости служебный ключ, разрешённый каталог и проверка связи. Публичный каталог не требует персональных данных клиента. Ключ хранить зашифрованным; адрес проверять по правилам безопасных серверных запросов из раздела 3.8.
- [ ] Для разных проектов явно выбирать подключение и доступные товары. Если несколько собственных групп используют один каталог, можно разделять общий справочник товаров, но нельзя автоматически объединять их диалоги, согласия и разрешения на рассылку.
- [ ] Повтор создания заявки после сетевого сбоя не создаёт дубль: сохранять проект и устойчивый идентификатор обращения с обеих сторон. Использовать очередь повторов с ограничениями, а не задерживать подтверждение Callback API запросом в CRM.
- [ ] Не переключать текущее сообщество одновременно на второго отвечающего бота из CRM. Обратную передачу статусов добавить отдельным этапом с проверкой отправителя, защитой от повторов и журналом; неизвестные связи не угадывать.

#### Как будет работать подбор

1. Клиент пишет, например: «Нужен материал для укрепления, светлый, до 1500 рублей» или нажимает «Помогите выбрать». Это пример запроса, а не готовая рекомендация конкретного продукта.
2. Бот извлекает понятные параметры и задаёт только недостающие вопросы. Набор вопросов зависит от категории: задача, желаемые свойства, оттенок, объём, бюджет. Не спрашивать заново уже однозначно указанные данные; сохранять возможность изменить выбор.
3. Подбор использует категории и характеристики каталога, проверенные вашей командой/технологом правила применения и ограничения. Обязательные условия отсекают неподходящее; предпочтения определяют порядок оставшегося. Не делать вывод о совместимости материалов только по похожему названию или высокой популярности.
4. Бот показывает 2–3 подходящих товара: фото, название, конкретный вариант/объём, цена, краткая причина соответствия запросу. Кнопки: «Открыть в магазине», «Другие варианты», «Изменить запрос», «Менеджер». Если фото не загрузилось, остаётся текст и ссылка, а не срыв всего диалога.
5. Если точных совпадений нет, сказать об этом и предложить явно изменить одно условие. Более дорогой или не полностью подходящий вариант не выдавать за точное совпадение. При недостатке сведений — уточнение или менеджер.
6. При запросе менеджера передать цель, ответы, выбранные/предложенные товары и источник проекта/кампании в связанное обращение CRM. Создание обращения не равно созданию заказа, резерву товара или согласию на рекламные сообщения.

#### Правила данных и «умное» понимание текста

- [ ] В каталоге магазина вести понятные назначения, свойства, допустимые применения, ограничения и согласованные синонимы. Сведения, которых нет в карточках, заполнить/подтвердить с командой; бот не должен придумывать свойства, лечебный эффект, совместимость или отсутствие аллергии.
- [ ] Первую версию можно сделать на вопросах, кнопках, словаре синонимов и прозрачных правилах отбора. Понимание произвольного текста через языковую модель — дополнительный вариант на согласование, а не обязательная замена этих правил.
- [ ] Если выбрана языковая модель, она переводит запрос в допустимые параметры и формулирует объяснение только по возвращённым товарам. Идентификаторы, обязательные ограничения, цены, ссылки и наличие проверяет программа. Неуверенное понимание ведёт к уточнению; произвольные инструкции из текста клиента/описания товара не меняют права и действия интеграции. Отдельно согласовать провайдера, расходы, лимиты и состав передаваемых данных; контакты и полная история заказов для обычного подбора не нужны.
- [ ] Проверять одновременно цену, требуемые свойства и наличие **одного и того же варианта**. В текущем списке каталога проверки цены и наличия независимы, а в ответ включаются все варианты: одной установки `inStock=true` недостаточно для корректной карточки рекомендации. Не брать бюджетную цену отсутствующего варианта и остаток другого.
- [ ] Источник цены и доступности — магазин; учитываются активность варианта, резерв, срок скидки и правила соответствующего типа товара. Оптовые/персональные цены выдавать только после подтверждённой авторизации. Рекомендация не резервирует товар и не гарантирует наличие до оплаты.
- [ ] У чтения каталога — ограничение времени ответа, небольшой кэш с явным сроком актуальности и повторная проверка перед выдачей конкретного предложения. Если актуальность не подтверждена, не обещать цену/остаток; предложить открыть карточку магазина или связаться с менеджером. Сбой магазина не останавливает другие функции бота.
- [ ] Условия покупки, итоговая цена и применение промокода подтверждаются магазином. Нельзя просто вычесть процент бота из уже акционной цены без проверки правил совместимости скидок.

#### CRM, аналитика и порядок выпуска

- [ ] Первый выпуск: каталог только для чтения → проверенные правила подбора → карточки со ссылкой → существующий вызов менеджера. Не трогать создание заказов, оплату и остатки.
- [ ] Второй: ограниченный API обращений → привязка проекта/сообщества/пользователя → передача ответов и товаров → сопоставление VK-менеджера с сотрудником CRM. Сохранить закрепление за первым ответившим; определить одну сторону, управляющую ответственным, и порядок синхронизации.
- [ ] Клиента CRM связывать через подтверждённый способ; одинаковое имя, введённый телефон или знание номера заказа не считаются доказательством владения профилем. Подбор публичных товаров должен работать без такой привязки.
- [ ] В аналитику и Excel добавить запрос подбора, нормализованные параметры без лишних персональных данных, показанные варианты, отсутствие совпадений, изменение условий и запрос менеджера. Для измерения переходов/заказов отдельно добавить подтверждённую связь событий магазина с рекомендацией; сам показ кнопки не считать кликом или продажей.
- [ ] Статус заказа, подтверждённая покупка и выручка — последующий этап с проверкой принадлежности заказа и согласованной атрибуцией. Данные заказа не открываются одному проекту только потому, что пользователь общался с другой группой.

Приёмка: товары действительно соответствуют задаче и обязательным условиям; проверены неполные характеристики, отсутствующий нужный вариант, разные цены/остатки вариантов, окончание акции, пустой результат, тайм-аут магазина, повторное обращение и несколько проектов. Исторические рекомендации сохраняют свой вариант и снимок показанных данных; повторный просмотр карточки уточняет текущее состояние. Ни одна проверка на копии не отправляет рабочие сообщения и не создаёт настоящую заявку.

## 4. Идеи для дальнейшей автоматизации — ещё не утверждены

Ниже — предложения, а не разрешение на их реализацию или запуск. Часть потребует уточнения магазина, CRM и доступных API. Уже работающие рассылки, отписки, визуальные сценарии, вызов менеджера и получение подарка после подписки не считаются новыми задачами: предлагается расширить их.

### А. Надёжность и диагностика — рекомендуемый первый приоритет

1. **Общая надёжная обработка событий.** Сохранять входящее событие до подтверждения его приёма, обрабатывать очередью, различать временную и постоянную ошибку. Расширить защиту от повторов на весь путь комментария, диалога и подарка; не обещать бессрочную гарантию «ровно один раз» от одного только `random_id` VK.
2. **Диагностика проекта.** Состояние ключа, Callback API, очередей, последней успешной отправки, свободного места и резервных копий. Долгое отсутствие комментариев само по себе не считать доказанным сбоем.
3. **Уведомления владельцу.** Просрочен ключ, отправки остановлены, растут ошибки, закончились промокоды, не проходит резервное копирование. Канал уведомлений выбрать отдельно; повторные сигналы объединять, чтобы не создавать поток одинаковых сообщений.
4. **Общая аварийная пауза.** Пауза отдельного проекта уже входит в текущий этап; остановка всех проектов одной кнопкой владельца остаётся предложением. Показать, что уже начатый сетевой запрос может завершиться, а текущая пауза не накапливает входящие события для последующей обработки.
5. **Автоматические резервные копии с проверкой восстановления.** Отдельно согласовать место хранения, срок хранения и доступ. Копии файлов и базы должны быть пригодны для совместного восстановления; для PostgreSQL использовать согласованный способ резервного копирования, а не считать обычный архив работающего тома достаточным. [Документация Docker о резервном копировании томов](https://docs.docker.com/engine/storage/volumes/).

### Б. Акции и промокоды

6. **Расписание кампаний.** Дата начала и окончания, часовой пояс, разрешённые часы, автоматическая остановка акции и лимит выдач. Явно определить судьбу уже заработанного подарка после окончания акции; повторно проверять актуальность перед отправкой.
7. **Уникальные промокоды.** Загрузка списка, один код на клиента, защита от одновременного получения одного кода разными людьми, учёт остатков. При исчерпании — остановить выдачу и уведомить владельца. Погашение кода учитывать только по данным магазина, а не по факту отправки.
8. **Гибкая защита от повторов.** Не только «один раз навсегда», но и «не чаще раза в заданный период» в рамках кампании/проекта. Явные лимиты и журнал причин пропуска.
9. **Проверка перед публикацией.** Тестовый комментарий, предпросмотр текста и файла, проверка ссылки, срока акции, доступных кодов и конфликтов условий — без реальной рассылки.

### В. Общение и сопровождение клиента

10. **Конкретные автоматические цепочки.** Само расширение конструктора уже обязательно и описано в разделе 3.8. Какие именно напоминания, анкеты и заявки запускать в каждом проекте, выбрать отдельно: наличие нового блока не включает его автоматически для клиентов.
11. **Запланированные сообщения и ограниченные цепочки.** Например, одно заранее согласованное напоминание о запрошенном, но не полученном подарке. Только при актуальном разрешении VK и подходящем согласии на сообщения; с лимитом частоты, тихими часами и отменой после получения подарка. Не превращать комментарий или переход по ссылке в безусловное право писать.
12. **Метки и сегменты.** «Получил подарок», «Нужен менеджер», «Интересовался категорией», «Сделал заказ» — последняя метка только при подтверждённой интеграции. Выбор аудитории рассылки по сегментам остаётся внутри проекта и учитывает отписки.
13. **Рабочее время менеджеров.** Сообщение клиенту о времени ответа, очередь обращений, уведомление ответственному и эскалация владельцу, если долго нет реакции. Сохранить правило закрепления за первым ответившим; другой алгоритм распределения вводить только после согласования.
14. **База ответов.** Доставка, оплата, возврат, размеры, уход за товаром. Сначала управляемые ответы и сценарии, затем при необходимости помощник на основе утверждённых материалов. При отсутствии достоверного ответа — менеджер; не выдумывать цены, наличие и скидки. Рассылки и изменение ключей не поручать такому помощнику без явного контроля.

### Г. Связь с магазином и оценка результата

15. **Дополнительные возможности каталога.** Подбор под задачу и исследованная связь с собственным сайтом/CRM уже зафиксированы в разделе 3.9. Подбор комплектов, персонализация по подтверждённой истории покупок и оптовые предложения — отдельные расширения, которые требуют согласованных правил и прав доступа.
16. **Заказы и CRM.** Создание заявки, передача согласованных данных менеджеру, уведомления об изменении статуса заказа. Доступ к заказу проверять по подтверждённой связи клиента с заказом, а не просто по введённому номеру. Платежи, возвраты и отмену заказа отдельно согласовать — не включать автоматически в понятие «автоматизация».
17. **Продажи и окупаемость.** Подробная аналитика работы бота и её Excel-выгрузка уже обязательны, см. раздел 3.6. Расширение до заказов, применения кодов, выручки и возвратов требует данных магазина и согласованных правил привязки продажи к кампании. Не считать каждую покупку после переписки результатом бота автоматически.

## 5. Предлагаемая очередность

Текущий приоритет пользователя — только несколько групп в одной панели. Остальное сохраняется как план, без включения в этот выпуск и без календарного срока.

1. **Несколько групп и перенос SARKISIAN — текущий этап**: реестр с шифрованием, отдельные схемы PostgreSQL/файлы SQLite, настройки VK, маршруты, очереди и файлы проектов, единый вход и переключатель. Сначала проверка кода и миграции на копии, затем отдельное окно обновления VPS; развёртывание сейчас не выполняется.
2. **Плюс-слова и Excel-экспорт клиентов — будущий этап**. Пустые плюс-слова сохраняют текущие условия; при согласовании добавить проверку комментария в интерфейсе. Выпускать небольшими проверяемыми обновлениями с сохранением данных.
3. **Подробная аналитика и Excel-отчёты — будущий этап**: сначала определить показатели и добавить недостающую историю событий, затем сводки и детализацию. Старые сведения доступны только в сохранённом объёме; новые показатели начнут накапливаться после внедрения учёта, внутри выбранного проекта.
4. **Первая очередь расширения сценариев — будущий этап**: дополнительные условия, проверка ответов, работа с переменными, готовые шаблоны и улучшенный симулятор. Выбрать полезные реальные диалоги; не ждать магазина/CRM ради этих возможностей.
5. **Следующая очередь конструктора, доступы команды и диагностика**: повторно используемые цепочки, надёжные ожидания и развилки по времени; состав выбрать по потребности и готовности очереди. История событий и разделение проектов обязательны для этих действий.
6. **Расписание кампаний, уникальные промокоды и ограниченные автоматические цепочки** — выбрать сценарии, согласовать тексты и условия отправки.
7. **Подбор из магазина и интеграция CRM**, по этапам раздела 3.9: сначала проверка каталога и чтение товаров, затем обращения, после — статусы заказов/заказная аналитика, если согласованы. Читающий подбор не требует ждать всех остальных автоматизаций, но в текущий выпуск нескольких групп не входит. База ответов — отдельное расширение.

Масштабирование сервера оценивать по измеренной нагрузке: объёму событий и рассылок, файлам, скорости API и потреблению памяти, а не только по числу групп. Общий домен можно сохранить при изменении внутреннего устройства сервиса.

## 6. Что нужно определить перед соответствующим этапом

- Порядок подключения новых групп и ожидаемая активность — без необходимости уточнять это для сохранения плана.
- Какие сотрудники действительно будут заходить в панель и что им разрешено делать.
- Подтверждение предложенного сопоставления плюс-слов: целое слово/фраза, а не часть слова.
- Приоритетные аналитические отчёты, часовой пояс, правила конверсий/неактивности и срок хранения детализации; какие поля разрешены сотрудникам в выгрузке.
- Два-три реальных диалога для первой очереди конструктора и порядок блоков/шаблонов; расширение уже в обязательном плане, эти примеры нужны для выбора первого выпуска.
- Нужны ли сроки кампаний и уникальные промокоды; откуда магазин будет передавать данные об использовании кода.
- Какой адрес API и какая версия собственного сайта/CRM реально развёрнуты; локальный NestJS API найден, но его доступность и данные на VPS не проверены. Для других проектов — их каталоги и разрешённые подключения.
- Кто заполнит/проверит назначения и свойства товаров, какие первые задачи покупателей покрыть подбором; нужна ли языковая модель для свободного текста или достаточно управляемых вопросов и синонимов.
- Порядок создания обращения без телефона, связь менеджеров двух систем и способ подтверждения принадлежности профиля/заказа.
- Канал уведомлений о сбоях, расписание и место хранения резервных копий.
- Конкретные автоматические сообщения, их назначение, согласие получателей, частота и условия остановки.

Цель — автоматизировать повторяющиеся действия и вовремя показывать исключения человеку. Недоступность VK, отзыв прав, спорный запрос клиента или неизвестные данные магазина не должны приводить к обходу ограничений или выдуманному ответу.
