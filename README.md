# VK Бот

VK-бот для нескольких сообществ в одной веб-панели: визуальные диалоги, кампании по комментариям, клиенты и рассылки отдельно для каждой группы. FastAPI, PostgreSQL и Docker Compose; редактор работает в браузере без отдельного Node.js-сервера и внешних CDN.

Согласованные будущие изменения и идеи автоматизации: [план доработок](ПЛАН_ДОРАБОТОК.md). Это план, а не перечень уже включённых функций.

## Что есть сейчас

- обработка событий Callback API VK;
- проверка подписки на сообщество;
- отправка промокода в личные сообщения;
- защита от повторной обработки комментариев;
- единая панель `/projects`, отдельные страницы проектов `/p/<id>/admin`, общий вход владельца, сессия и выход;
- отдельные кампании с собственными промокодами, сообщениями, вложениями и фильтрами;
- защита от повторной выдачи промокода одному пользователю;
- плюс-слова, стоп-слова и минимальная длина комментария;
- отправка VK-вложений вместе с сообщением;
- статистика и журнал последних событий;
- контейнеризация приложения и PostgreSQL.
- визуальные сценарии: сообщения, вопросы, условия, промокоды, вызов менеджера и завершение;
- кнопки перехода к блоку и открытия ссылки, файлы прямо с компьютера;
- сохранённые состояния клиентов, черновик/публикация и интерактивный предпросмотр;
- каталог клиентов: имя, фамилия, фото, ссылка VK, доступный телефон, поиск и карточки;
- рассылки всем подтверждённым получателям бота или выбранным клиентам: вложения, тест, подтверждение запуска, пауза, отмена и журнал;
- диалоги с входящими сообщениями, ошибками и возвратом от менеджера к боту.

## Несколько групп в одной панели

Один проект соответствует одному сообществу VK. На `/projects` владелец добавляет группу, задаёт название, числовой ID, её токен, секрет Callback API и код подтверждения. `<id>` в адресах панели и Callback — внутренний ID проекта, а не VK ID сообщества. Все группы работают на существующем домене и в одном Compose-стеке.

Новый проект создаётся **на паузе**. Подготовьте его настройки, кампании и сценарии, затем включите явно. Панель на паузе доступна для просмотра и подготовки; автоматические ответы, рассылки, фоновые обновления профилей и реальные тестовые отправки VK остановлены. Доступны подтверждение Callback API и явная проверка принадлежности токена через `groups.getById`. Отписки «Стоп»/кнопкой и события разрешения/запрета сообщений учитываются без исходящих ответов.

Обычные события Callback с правильными ID сообщества и секретом на паузе получают `ok` и **отбрасываются**. У бота нет сохраняемого входящего журнала для последующей обработки: обычные сообщения, комментарии и вступления за время паузы не ставятся в очередь и не проигрываются после включения. Исключение — отписки и изменение разрешения сообщений: эти сведения сохраняются, чтобы не потерять отказ клиента. Уже сохранённые история и очередь рассылок остаются: после включения проекта готовые к работе задания продолжаются автоматически с учётом отписок; отдельная пауза или отмена самой рассылки сохраняется. Уже начатый сетевой запрос может завершиться.

В разделе проекта показан его отправитель. Клиенты, отписки, состояния диалогов, кампании, сценарии, подарки, файлы и очереди принадлежат выбранной группе. Один человек может быть клиентом нескольких групп с независимыми разрешениями и историей. Смена проекта в одной вкладке не переключает проект другой вкладки: он задан в URL. Проверка подключения устанавливает принадлежность токена группе; она не подтверждает права отправки, работу Callback API или разрешение конкретного получателя.

Для PostgreSQL выбрана изоляция отдельными схемами в одной базе. Первый импортированный проект сохраняет прежние таблицы и файлы; для новых создаются свои схемы. Это сознательный выбор вместо добавления `project_id` в каждую существующую строку. При SQLite новые проекты используют отдельные файлы БД, а первый импортированный — прежнюю базу. Реестр проектов общий. Изоляция данных не является разграничением доступа сотрудников: владелец имеет доступ ко всем проектам.

Адрес `/vk/callback/<id>` обслуживает только указанный проект с проверкой ID сообщества и его секрета. Прежние `/admin` и `/vk/callback` привязаны только к импортированной группе; они не следуют за выбором проекта в браузере. На новой установке начните с `/projects`.

Копирование кампаний/сценариев между проектами, выгрузки подробной аналитики и роли сотрудников остаются в [плане доработок](ПЛАН_ДОРАБОТОК.md). Выгрузка базы клиентов в Excel уже реализована.

## Клиенты и рассылки

В «Клиентах» видны известные боту участники диалогов и комментариев. Нажмите «Обновить данные VK» для фонового обновления имени, фамилии, фотографии и доступных контактов через `users.get`. Телефон не гарантирован: сохраняются только возвращённые VK `mobile_phone` / `home_phone` либо номер, добровольно оставленный клиентом в ответе сценария с именем `phone`, `telephone` или `телефон`. Скрытые номера не извлекаются. Если VK перестал возвращать ранее доступный номер, такой номер очищается при обновлении. [Поля профиля VK](https://github.com/VKCOM/vk-api-schema/blob/master/users/objects.json).

Карточка клиента показывает последние входящие события и результаты рассылок. Кнопка «Диалоги и менеджеры» открывает прежние обращения, ответы сценария и «Вернуть к боту». Фото загружается браузером с HTTPS-адреса, полученного от VK, без Referer.

В «Рассылках» напишите текст, при необходимости загрузите файл, выберите всех получателей или отмеченных в списке клиентов. Доступны `{first_name}`, `{user_name}`, `{last_name}`. «Предпросмотр и проверка» сохраняет неизменяемый черновик со снимком аудитории, **не отправляя сообщения**. В предпросмотре можно отправить один тест указанному ID. Для настоящей отправки требуется отдельное подтверждение согласия аудитории и нажатие «Запустить рассылку». Старый диалог или разрешение VK сами по себе не означают согласие на рекламные сообщения. До 10 000 получателей на один запуск, до 4000 символов исходного текста, один файл до 50 МБ; типы вложений те же, что у сценариев.

Аудитория — только пользователи с сохранённым подтверждением успешного исходящего сообщения бота. Менеджеры, отписавшиеся и деактивированные профили исключаются. Перед каждой отправкой проверяются актуальная отписка и `messages.isMessagesFromGroupAllowed`. Запрет/недоступность получателя даёт пропуск, а не обход ограничений VK. События Callback API `message_allow` / `message_deny` также обновляют локальные данные (рекомендуется включить); независимо от них разрешение перепроверяется в API. Разрешение сообщений заново не отменяет отписку от рассылок.

Кнопка отписки и строка про «Стоп» добавляются автоматически. Команды `Стоп`, `stop`, `/stop`, `Отписаться` и кнопка отключают последующие рассылки, не сбрасывая сценарий и менеджера. Вернуть их может сам клиент командой `Подписаться на рассылку` или `/subscribe`. Администратор может исключить клиента из карточки, но не подписать обратно без его действия. Обычные запрошенные ответы бота и промокоды не блокируются отпиской от рассылок.

Очередь, результаты, отписки и профили хранятся в БД проекта. Для каждой включённой группы работает свой фоновый исполнитель с арендой в её БД: примерно не чаще одного сообщения в секунду на проект (API-запросы могут снижать скорость). Это не отменяет индивидуальных ограничений VK. При временных ошибках — до 4 попыток с задержкой. Ошибки токена, доступа, flood control или captcha останавливают рассылку на паузе, без автоматического обхода. Повтор использует сохранённый текст, вложение и тот же `random_id`; VK-дедупликация не является бессрочной гарантией «ровно один раз». После аварийного завершения незаконченная отправка может ждать истечения аренды до 5 минут. На паузе/при отмене уже начатый сетевой запрос может завершиться; ранее отправленные сообщения не отзываются. «Доставлено VK» означает принятие API, а не прочтение.

При обновлении данные кампаний и диалогов первого проекта сохраняются в прежнем хранилище. Старые подтверждённые выдачи промокодов восстанавливаются автоматически. Полной истории старых приветствий/тестов нет, поэтому неподтверждённые старые отправки не включаются в аудиторию автоматически. Все новые успешные личные отправки бота учитываются в его проекте. Проверка на SQLite не заменяет репетицию переноса PostgreSQL; перед обновлением VPS сохраните все схемы БД, том `bot_data` и отдельно ключ шифрования проектов.

Новых обязательных ENV нет. Фоновый исполнитель включён по умолчанию; `BACKGROUND_JOBS_ENABLED=false` отключает и рассылки, и обновление профилей для локальных проверок. Для Docker Compose эта необязательная переменная также поддерживается. После обновления репозитория пересоберите контейнер приложения; перезапуска старого образа недостаточно.

## Конструктор сценариев

1. Откройте «Сценарии» → «Новый сценарий». Появится пример диалога.
2. Выберите блок для редактирования справа. Добавляйте блоки кнопками над схемой.
3. Перетаскивайте блок за заголовок. Для связи нажмите круг справа у нужного выхода, затем круг слева у следующего блока. Переход можно выбрать и в форме. Перетаскивание пустого поля перемещает схему; масштаб меняется кнопками снизу или Ctrl + колесо. Ctrl+Z отменяет изменение графа, Ctrl+S сохраняет черновик.
4. В блоке «Вопрос» укажите имя ответа (например `size`). Ответ доступен в следующих сообщениях как `{size}`. Ветки проверяют наличие указанных слов без учёта регистра; первая подходящая ветка имеет приоритет, иначе используется «Другой ответ».
5. Условия проверяют слова в последнем входящем сообщении, подписку или предыдущую выдачу промокода выбранной кампании.
6. «Предпросмотр» выполняет тот же интерпретатор, но не вызывает VK и не выдаёт реальные промокоды. Подписку можно переключить в окне теста. В каждом новом тесте выдачи промокодов считаются заново.
7. «Сохранить» меняет только черновик. «Опубликовать» проверяет все связи, ссылки, кампании и циклы и включает сценарий. В каждом проекте одновременно активен один входной сценарий; публикация другого приостанавливает предыдущий в том же проекте. Правки в черновике не меняют работающий диалог. Публикация не снимает паузу проекта.

Начало — первое личное сообщение или команда `меню`, `начать`, `старт`, `/start`. Бот запоминает текущий шаг в PostgreSQL, включая ответы пользователя. После публикации новой версии следующее обычное сообщение начинает новый сценарий; старые кнопки не выполняют действий. Повторная доставка одного события VK не запускает диалог заново. Автоматические циклы без ожидания ответа запрещены.

Ограничения редактора: до 100 блоков, 5 кнопок под одним сообщением, 10 веток ответа. Кнопка ссылки открывает сайт и не переводит клиента на следующий шаг. Автоматический переход между разными сценариями, платежи и VK Mini Apps в эту версию не входят.

Изображения отправляются как фотографии, видео и аудио — как файлы VK (до 50 МБ). Метод `video.save` требует пользовательского токена, поэтому бот с ключом сообщества использует загрузку документов. Предпросмотр показывает названия вложений; фактическая загрузка в VK выполняется только при настоящем ответе.

## Менеджер и кампании

В «Общение» укажите числовые VK ID менеджеров через запятую или с новой строки (до 50). Каждый должен разрешить сообщения сообщества и иметь доступ к переписке сообщества. Старое поле/ENV `OPERATOR_USER_ID` сохранено: один ID продолжает работать, теперь принимается и список. Повторяющиеся ID убираются; некорректный список не сохраняется.

При вызове уведомление получают все менеджеры. Первый, кто отвечает клиенту от сообщества или нажимает «Взять в работу» в уведомлении, закрепляется за обращением. Остальным приходит сообщение, что обращение уже взято. Для определения автора ответа включите событие Callback API **`message_reply`** наряду с `message_new`. Автоматическое закрепление использует необязательное поле `admin_author_id`; если VK его не передаёт, используйте кнопку. Источник формата: [официальная схема сообщений VK](https://github.com/VKCOM/vk-api-schema/blob/master/messages/objects.json).

Закрепление хранится в БД, видно в разделе «Клиенты» и не перезаписывается вторым менеджером. Это учёт ответственного в боте, а не запрет другим администраторам отвечать в интерфейсе VK. Обработка защищена от одновременного взятия, повторных событий и старых кнопок предыдущего обращения. Ошибка уведомления одного менеджера не прерывает рассылку остальным и не снимает закрепление; подробности видны в журнале клиента.

После вызова бот молчит до команды `меню` или действия «Вернуть к боту» в разделе «Клиенты». Они закрывают обращение, снимают закрепление и аннулируют старую кнопку. При новом вызове уведомление снова получают все менеджеры. Сам менеджер отвечает из сообщений сообщества VK, не из этой панели. Журнал клиента показывает входящие сообщения, события взятия и ответы настроенных менеджеров во время обращения; это не полный архив переписки VK.

В «Кампании» настройте сообщение, промокод, ссылку, файл и фильтры. **Пустой ID поста** создаёт общую кампанию для новых комментариев под любыми постами и собственными видео сообщества. Такая кампания может быть только одна (в БД обозначается `post_id=0`; в форме вводить `0` не нужно). Для отдельного поста укажите его положительный ID. Кампания конкретного поста всегда имеет приоритет: её приостановка блокирует выдачу по этому посту, общая кампания её не подменяет. Для видео используется только общая кампания, даже если номер видео совпадает с номером поста.

Для комментариев к видео включите **`video_comment_new`** в Callback API. События нормализуются по официальной схеме [комментариев VK](https://github.com/VKCOM/vk-api-schema/blob/master/callback/objects.json). Отдельного события комментариев к клипам в этой схеме нет. Комментарий под клипом будет обработан, **если VK передаст его как `video_comment_new`**. Доставка таких событий не гарантируется кодом; нужна проверка на реальном клипе. Комментарий на стене под постом с прикреплённым роликом — это `wall_reply_new`, он обрабатывается как комментарий к посту.

Если нет ни отдельной, ни общей кампании, комментарий пропускается. Защита от повторной выдачи действует **внутри кампании** и учитывает комментарии ко всем охваченным постам/видео, а также выдачи через диалог. Изменение ID поста существующей кампании не сбрасывает историю выдач. Тестовая отправка берёт выбранную кампанию и ID из формы, не меняет счётчики выдач.

Комментарии хранятся в `comment_events` проекта с уникальным ключом «тип + владелец + публикация + комментарий» и ID кампании. При обновлении записи из прежней `processed_comments` копируются в новую таблицу без удаления старой; повторный запуск миграции не дублирует записи. Это сохраняет статистику и защиту от повторной обработки, не смешивая одинаковые номера комментариев к постам и видео. Для первоначального переноса сохраните прежний `VK_GROUP_ID`; дальнейшая обработка использует настройки выбранного проекта.

Файлы хранятся в томе `bot_data`; сценарии и состояния — в `postgres_data`. Удаление ссылки на файл из блока не удаляет файл с диска, поскольку его может использовать опубликованная версия. Схема БД дополняется при запуске; существующие кампании и настройки сохраняются. Общие старые `PROMO_*` не заменяют настройки кампаний.

## Приглашение за подарком в чат

В кампании выберите `Способ выдачи → Пригласить в чат ответом на комментарий`. Сохранённые ранее кампании остаются в режиме прямого личного сообщения: обновление само по себе не начинает публиковать ответы. Новых ENV нет.

В каждой кампании можно редактировать 1–10 вариантов приглашения (до 2000 символов, обязательная переменная `{chat_url}`). Предложены четыре готовых текста. Вариант выбирается случайно и сохраняется вместе с ожидающим подарком. Другие переменные личного сообщения не подставляются в публичный ответ. Выбор случайный, не гарантия отсутствия одинаковых текстов подряд и не обход ограничений VK.

После проверки комментария бот создаёт `pending_gifts` и отвечает адресно через [wall.createComment](https://github.com/VKCOM/vk-api-schema/blob/master/wall/methods.json), с `reply_to_comment`, `from_group` и стабильным `guid`. В режиме приглашения неподписанные тоже получают ссылку; подписка обязательна при выдаче в чате. Прямой режим по-прежнему пропускает комментарии неподписанных. Необходимо разрешение ключа сообщества на стену и сообщения. Только одна активная запись на пользователя/кампанию; повторные комментарии и Callback-события не публикуют приглашение повторно. Если публичная отправка не удалась, это видно в статистике, а ожидающий подарок сохраняется. Автоматических повторов публичного ответа нет.

В «Настройки» → «Ссылка на чат» задаётся значение `{chat_url}` для всех приглашений, например `https://vk.me/sarkisian.brand`. При пустом поле используется `https://vk.me/club<GROUP_ID>` текущего бота. Допускается полный HTTPS-адрес до 500 символов без пробелов и встроенных логина/пароля; параметры ссылки сохраняются. Значение хранится в `bot_settings`, применяется сразу к новым приглашениям, не требует ENV или миграции и не меняет уже опубликованные комментарии/ожидающие подарки. Старые формы без этого поля не сбрасывают значение. В кампаниях показан текущий адрес и переход к его настройке.

Изменение ссылки не переключает проект между сообществами: для автоматической выдачи она должна вести в личные сообщения группы, указанной в настройках этого проекта. Для другого проекта нужны его ключ, сообщество и Callback API; ожидающие подарки между проектами не переносятся. Ссылка сама по себе не предоставляет согласия. Первый запрос подарка срабатывает только на входящее личное `message_new`: «Подарок», «Получить подарок», `/gift`, «Начать», «Старт», `/start` или кнопку с `action=claim_gift`; учитывается также стартовый payload `{"command":"start"}`. Событие проверяется по сообществу и фактическому отправителю. Пользователь не может передать ID чужого подарка для выдачи. Если подписки нет, этот запрос сохраняется для последующей автоматической выдачи.

Выдача проверяет текущую активность кампании, подписку и историю отправок. При нескольких подарках — один за запрос с кнопкой следующего. Без подписки запоминается `awaiting_subscription=true` и отправляется предложение подписаться с кнопками ссылки и повторной проверки. После [события VK `group_join`](https://github.com/VKCOM/vk-api-schema/blob/master/callback/objects.json) (`join`, `accepted`, `approved`) бот повторно проверяет `groups.isMember`, текущее разрешение `messages.isMessagesFromGroupAllowed` и выдаёт ранее запрошенный подарок автоматически. Заявки `request`, ответы `unsure`, чужие сообщества, события без ID и вступления без явного запроса подарка ничего не отправляют. Если событие не пришло или VK ещё не подтверждает подписку, остаётся кнопка ручной проверки. Повторное вступление не выдаёт тот же промокод снова.

В Callback API включите **«Вступление в сообщество» (`group_join`)**. Новых ENV нет. Миграция добавляет маркер ожидания и восстанавливает его для старых подарков с завершённым явным запросом, но без выдачи; для просто оставивших комментарий он не включается. Выдача независима от `chat_enabled`, не перезапускает сценарий и не снимает менеджера. `меню` возвращает обычный диалог. Отключённая/удалённая акция отменяет запрошенный подарок. Смена режима на прямой не отменяет уже ожидающие подарки.

При успешной отправке атомарно записываются `PromoDelivery`, `comment_events.status=sent`, состояние подарка и обработанное событие диалога. При ошибке VK/сети сохраняются подготовленный текст/вложение и привязка входящего события к подарку; повтор использует тот же `random_id`. Это предотвращает повторную выдачу при обычных повторах Callback и повторной команде клиента в пределах дедупликации VK; распределённая транзакция между VK и БД невозможна, абсолютная exactly-once доставка при авариях не гарантируется. Подарок не теряется при перезапуске. Оба пути используют общую блокировку пользователя, включая PostgreSQL advisory lock.

Приглашения под видео используют [video.createComment](https://github.com/VKCOM/vk-api-schema/blob/master/video/methods.json), который принимает только пользовательский токен. В «Проекты → Подключение и настройки проекта → Ответы под видео» можно сохранить собственный пользовательский токен администратора с доступом к видео, полученный разрешённым VK способом. Он хранится внутри зашифрованных настроек проекта, не в ENV, не отображается обратно в HTML и не подменяет токен сообщества. Пустое поле сохраняет ключ; отдельная галочка удаляет. Бот вызывает этим токеном только `video.createComment` для собственного видео группы, с `from_group=1`, `reply_to_comment` и стабильным `guid`. Проверка подключения проекта проверяет ключ сообщества, а не права пользовательского токена. Нужен реальный тест в VK; наличие поля не гарантирует, что VK выдаст вашему приложению нужные права.

Без пользовательского токена приглашение для подходящего `video_comment_new` отправляется через ключ сообщества в личные сообщения **только при разрешении VK**, с кнопкой «Получить подарок» (`video_invited_dm`). Сохранённая отписка или запрет сообщений блокируют этот резервный путь. Если личка недоступна, сохраняется ожидающий подарок и статус `video_waiting_chat`, но приглашение не отправляется. Разместите ссылку на чат в описании видео: после входящего «Подарок»/«Начать» клиент сможет получить его по прежним условиям. Ошибка пользовательского токена записывается в статистику, без попытки публиковать от личного имени. Повторные комментарии не дублируют ожидающее приглашение. Старые события со статусом `invite_unsupported` не переигрываются. Прямая отправка для видео остаётся прежней. Проверяйте весь путь новым комментарием в тестовом режиме; ручной тест кампании проверяет только личное сообщение. Клипы зависят от получения `video_comment_new` и доступности видео для API.

### Плюс-слова и Excel

Поле «Плюс-слова» задаётся отдельно в каждой кампании. Пусто — ограничения по плюс-словам нет; иначе достаточно одного слова или фразы. Разделители — запятая или новая строка. Регистр не важен, `е`/`ё` равнозначны, повторные пробелы нормализуются. Сопоставляются целые слова, без склонений: `крем` не совпадает с `крема`. Стоп-слова имеют приоритет; минимальная длина, тестовый режим, подписка и защита от повторов сохраняются. Фильтр действует на комментарии к постам и видео до отправки приглашения или создания подарка; на обычный диалог и ручной тест не распространяется. Причина пропуска — `plus_word_missing` («Нет плюс-слова»). Миграция добавляет `campaigns.plus_words` с пустым значением во всех проектах, не меняя существующее поведение.

В «Клиенты» кнопка «Скачать Excel» скачивает `.xlsx` всех клиентов **текущего проекта**, соответствующих полям поиска и фильтра «Кому бот писал»; пагинация и отметки строк не ограничивают выгрузку. Экспорт содержит ID, имя, фамилию, ссылку VK, доступный телефон и его источник, ссылку на фото, даты (UTC), статусы разрешения сообщений/отписки/профиля. Второй лист содержит параметры выгрузки. Новые данные у VK не запрашиваются и фото не скачиваются; это не экспорт подробной аналитики. Ссылки защищены входом администратора и `no-store`. Текстовые ячейки, включая телефоны и строки с `=`, записываются как текст, не формулы. База читается порциями, готовый файл выгружается потоково; новые ENV не нужны.

## Запуск на VPS

```bash
docker network create proxy
cp .env.example .env
nano .env
docker compose up -d --build
docker compose logs -f vk-bot
```

Панель открывается через домен в Nginx Proxy Manager: `https://vkbot.it-sarkisian.ru/projects`. Порт 8000 доступен внутри Docker-сети, наружу не публикуется. Логин и пароль берутся из `ADMIN_USERNAME` и `ADMIN_PASSWORD`. Portainer управляет общим Compose-проектом. Команды выше предназначены для установки; перед обновлением существующего VPS выполните порядок резервного копирования и переноса ниже. Новых обязательных ENV для нескольких групп нет.

## Nginx Proxy Manager

В Portainer создай Stack из файла `deploy/nginx-proxy-manager.yml`. Перед этим один раз создай общую сеть:

```bash
docker network create proxy
```

Для новой установки после запуска Nginx Proxy Manager открой `http://IP_VPS:81`, создай Proxy Host для выбранного домена (например, `vkbot.it-sarkisian.ru`), укажи схему `http`, имя контейнера `vk-bot` и порт `8000`. Затем запроси SSL-сертификат Let's Encrypt и включи Force SSL. Для уже работающей установки сохрани существующий Proxy Host: дополнительные группы не требуют новых доменов или прокси-стеков.

На VPS укажите в `.env` необязательный общий публичный адрес панели:

```dotenv
PUBLIC_BASE_URL=https://vkbot.it-sarkisian.ru
```

Это тот же существующий домен. Параметр задаёт основу отображаемых адресов Callback (`https://vkbot.it-sarkisian.ru/vk/callback/<id>`), когда HTTPS завершается на Nginx, а до приложения запрос идёт по HTTP. Он не создаёт новый домен, сертификат или сервер Callback в VK. При обновлении передайте значение контейнеру через Compose и пересоздайте приложение в согласованное окно.

Адрес должен содержать `http://` или `https://` и хост, при необходимости порт, без пути, query-параметров, фрагмента и логина/пароля. Для публичного VPS используйте HTTPS; HTTP подходит для локальной проверки, например `http://127.0.0.1:8766`. При пустом `PUBLIC_BASE_URL` панель использует основу URL входящего запроса (`request.base_url`): за прокси она может оказаться `http://…`. Явная настройка публичного URL устраняет эту зависимость; ради отображения ссылки не требуется включать доверие к произвольным заголовкам прокси.

В тексте сообщения доступны переменные `{user_name}`, `{first_name}`, `{promo_code}` и `{shop_url}`. Вложения в панели загружаются обычным файлом. Стоп-слова можно вводить по одному на строку. При включённой защите один пользователь получает промокод только один раз.

В `.env` обязательно заменить все значения `change_this_*`, задать учётные данные владельца панели и параметры PostgreSQL. `DATABASE_URL` должен быть:

```text
postgresql+psycopg://vkbot:ПАРОЛЬ@postgres:5432/vkbot
```

Для каждой новой группы в VK указывается её адрес `https://ВАШ-ДОМЕН/vk/callback/<id>` из панели, собственный секрет и код подтверждения. Старый `https://ВАШ-ДОМЕН/vk/callback` сохраняется только для группы, импортированной из прежней установки. Нужны события `wall_reply_new` (комментарии на стене), `video_comment_new` (комментарии к видео), `message_new` (входящие личные сообщения), `message_reply` (исходящие сообщения — для закрепления за ответившим менеджером), `group_join` (выдача ранее запрошенного подарка после подписки); рекомендуются `message_allow` / `message_deny`. Кнопки перехода и «Взять в работу» используют `text` и payload; отдельное событие `message_event` им не требуется. Форматы событий: [официальная схема VK API](https://github.com/VKCOM/vk-api-schema/tree/master/callback). Сохранение проекта в панели само по себе не регистрирует сервер Callback API в VK.

## ENV и ключ шифрования проектов

Инфраструктура остаётся общей: `DATABASE_URL`, `POSTGRES_*`, `ADMIN_USERNAME`, `ADMIN_PASSWORD`, `ADMIN_SESSION_SECRET`, необязательный `PUBLIC_BASE_URL`, `LOG_LEVEL`, `BACKGROUND_JOBS_ENABLED` и версия `VK_API_VERSION`. Вход владельца действует для всех проектов; отдельные учётные записи сотрудников и RBAC пока не реализованы. VK ID менеджеров в «Общение» относятся к обработке обращений в сообществе и не создают доступ в панель.

Токен VK, секрет Callback API и код подтверждения хранятся в реестре проектов зашифрованными Fernet. Ключ находится вне БД:

| Параметр | Назначение |
| --- | --- |
| `PROJECTS_ENCRYPTION_KEY` | Необязательный готовый ключ Fernet: 32 байта в URL-safe Base64. Это не произвольный пароль. Если задан, используется вместо файла. |
| `PROJECTS_KEY_FILE` | Необязательный путь к файлу ключа; по умолчанию `data/projects.key`, в контейнере `/app/data/projects.key`. При отсутствии ENV-ключа первая инициализация создаёт и сохраняет ключ в этом файле; следующие запуски читают тот же ключ. |

Нового обязательного ENV нет. При выборе своего пути ключ должен находиться на постоянном хранилище, доступном приложению после пересоздания контейнера. Сохраните отдельную защищённую резервную копию фактически используемого ключа, даже если файл по умолчанию уже входит в `bot_data`. Без него зашифрованные секреты восстановить нельзя. Не заменяйте и не удаляйте ключ при обычном обновлении: новый ключ не расшифрует прежние записи. Если реестр уже инициализирован, потеря или неверный ключ приводят к ошибке; восстановите исходный ключ из копии.

Прежние `VK_GROUP_ID`, `VK_GROUP_TOKEN`, `VK_CALLBACK_SECRET`, `VK_CONFIRMATION_CODE` нужны для однократного импорта существующей группы. Сначала сохраните их для миграции и проверьте результат на копии. После успешного импорта настройки группы изменяются в панели; изменение старого ENV не заменяет сохранённые секреты. Без `VK_*` конфигурация использует `VK_GROUP_ID=0` и пустые реквизиты: это отсутствие настроенной legacy-группы, а не реальное сообщество. После пустой первичной инициализации реестра позднее добавление `VK_*` не запускает импорт заново, поэтому при обновлении действующей установки не убирайте их до первого переноса. Новые группы добавляются через `/projects` без новых ENV, доменов, стеков и перезапуска контейнера. Проект с пустым токеном не получает токен первой группы.

Импорт также сохраняет прежние значения по умолчанию для общения, менеджеров, тестового режима и промо-настроек; существующие значения в `bot_settings` продолжают иметь приоритет. Новые проекты получают свои исходные настройки и не наследуют менеджеров или тексты первой группы. Старые ENV с реквизитами и настройками группы можно убрать **только после проверенного импорта**, сохранения резервных копий и сверки работы исходного проекта. Инфраструктурные ENV и используемый ключ шифрования остаются.

## Резервная копия и переход с одной группы

Этот порядок предназначен для будущего обновления VPS. Публикация кода и документации не означает, что миграция на рабочем сервере уже выполнена. В текущем Compose один контейнер приложения: на его пересоздание и миграцию требуется окно недоступности панели и Callback API.

1. Подготовьте образ и репетицию на отдельной копии базы и файлов, в отдельной рабочей папке/с отдельными томами. Для SQLite недостаточно изменить только имя основной БД в том же каталоге: файлы `project_<id>.db` лежат рядом с ней, а загрузки — в `data/projects/<id>/`. До запуска копии используйте фиктивные VK-реквизиты **во всех проектах**, отдельные учётные данные панели и `BACKGROUND_JOBS_ENABLED=false`. Для зашифрованного реестра одной замены `VK_*` в ENV недостаточно: рабочие секреты уже сохранены в БД. Исключите исходящий доступ копии к VK, пока её реквизиты не обезврежены. Не регистрируйте на копию живой Callback API. Тестовый режим комментариев не отключает остальные отправки; `BACKGROUND_JOBS_ENABLED=false` отключает фоновые задания, но не ручные отправки и обработку входящих событий.
2. До окна обновления проверьте восстановление и длительность переноса на копии. Зафиксируйте образ предыдущей версии, имя Compose-проекта, подключения к БД и существующим томам. Не создавайте новый стек ради второй группы.
3. В согласованное окно остановите запись и отправки приложения, дайте начатым операциям завершиться. Сделайте согласованную копию: полный логический дамп PostgreSQL **со всеми схемами и реестром проектов**, весь том `bot_data`, отдельно ключ Fernet и необходимые инфраструктурные секреты. Дамп только `public` потеряет новые проекты; архив работающего `postgres_data` сам по себе не заменяет проверенную копию PostgreSQL. Для SQLite сохраняются все файлы БД проектов вместе с файлами вложений при остановленной записи.
4. Обновите единственный контейнер с прежними БД и томами. На первый проверочный запуск оставьте `BACKGROUND_JOBS_ENABLED=false` и не возобновляйте приём рабочих Callback до сверки данных. Импортированный проект с полными реквизитами создаётся включённым, поэтому обычный старт с фоновыми задачами сразу разрешает продолжение его очередей. Не запускайте старые и новые обработчики/очереди одновременно. Первый проект использует существующие таблицы и файлы: их не нужно вручную переносить в новую схему или перенумеровывать. Старый Callback URL остаётся у импортированной группы.
5. Проверьте вход, список проектов, сохранённые кампании, сценарии, файлы, клиентов, отписки, ожидающие подарки, историю и очереди. `/health` недостаточно для проверки миграции. Проверьте два проекта с одинаковыми VK ID пользователей и номерами постов на изолированных тестовых данных. Возобновляйте реальные отправки после проверки состояния; новый проект требует отдельного включения.
6. Для отката остановите приложение и восстановите согласованный комплект БД, `bot_data`, ключа и совместимого образа. Если новая версия уже обрабатывала события или отправляла сообщения, сначала сверяйте актуальную историю: восстановление старого снимка без сверки может потерять изменения и повторить выдачи.

Ключ шифрования требуется сохранять с момента первого создания реестра. Автоматическое резервное копирование и ротация ключа этим обновлением не добавляются. Повторы VK в окно недоступности не являются гарантией нулевой потери событий.

## Проверки

```bash
python -m pip install -r requirements.txt pytest
python -m pytest -q
```

Основные тесты используют изолированную SQLite БД и подменяют VK API. Проверяют графы, авторизацию, публикацию, конфликты сохранения, диалоги, повторы событий, кнопки старых версий, промокоды и передачу менеджеру.

`tests/test_project_storage.py` проверяет импорт, шифрование, независимость данных, файлов и контекстов проектов на SQLite и PostgreSQL. PostgreSQL-ветка включается через `PROJECT_TEST_DATABASE_URL` на отдельном тестовом сервере; она создаёт и удаляет собственные временные базы. Без этой переменной PostgreSQL-проверки пропускаются. Локальный прогон этого этапа использует настоящий PostgreSQL 17; рабочая конфигурация Compose остаётся на `postgres:16-alpine`. Проверка на 17 не подтверждает прогон на 16 и не означает обновления PostgreSQL на VPS. Перед переносом нужна репетиция на версии и данных рабочей установки.

`tests/browser_projects.py` проверяет интерфейс нескольких проектов на отдельном локальном сервере `127.0.0.1:8766`, с временной SQLite БД, фиктивными реквизитами и отключёнными фоновыми задачами. Проверка пройдена в настольном и мобильном размерах окна; она не подтверждает подключение живого Callback API или реальные отправки VK. Скриншоты сохраняются в `data/review_projects/`.

`tests/browser_smoke.py` — браузерная проверка на отдельном локальном сервере `127.0.0.1:8765` с тестовой базой и пользователем `preview` / `preview-local-only`. Только для локальной разработки; не задавайте эти учётные данные на VPS. Нужны `playwright` и `python -m playwright install chromium`. Скриншоты сохраняются в `data/review/`.

`tests/test_broadcasts.py` проверяет учёт отправок, восстановление клиентов, отписки, авторизацию, состав аудитории, явный запуск, очередь, повтор после сбоя, паузу/отмену и обработку ошибок VK. `tests/browser_crm.py` проверяет новые экраны, загрузку, предпросмотр, тест, подтверждение, журнал и мобильную вёрстку с подменённым API. Для обоих браузерных скриптов запускайте локальный сервер с `BACKGROUND_JOBS_ENABLED=false` и фиктивным токеном, не с рабочими данными VK.
